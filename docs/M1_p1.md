## 1. Work package objective

Implement or complete the first M1 vertical slice: a deterministic, replayable, bounded tool environment that accepts a task, exposes approved tool contracts, validates proposed calls before execution, returns normalized observations, enforces step/time/permission limits, and records a redacted trace that can be replayed and scored.

This package is limited to the runtime tool/task harness and its contracts. It does not include model training, reward design, broad benchmark integration, or model release. Reuse the M0 artifacts and preserve their interfaces unless inspection proves a change is necessary.

### Success criteria

- Existing tests and interfaces remain compatible, or any intentional interface change is documented in `system_design.md` before code is changed.
- A seeded task can be reset and replayed with the same deterministic environment outcome.
- Unknown tools, malformed arguments, schema violations, semantic-bound violations, exhausted budgets, and tool exceptions fail in an explicit and typed way; no invalid call reaches the tool implementation.
- Tool execution is bounded by configured step and timeout limits. Write or external side-effecting operations remain disabled unless specifically authorized by the existing project policy.
- Trace events contain enough provenance and normalized inputs/results/errors to support diagnosis and replay, while redaction prevents secrets and disallowed sensitive data from being stored.
- Tests cover nominal operation, deterministic replay, validation failures, permission denials, step/time limit behavior, tool exceptions, and redaction edge cases.
- Acceptance evidence is recorded in the relevant M1 row in `docs/plan.md` and M1 checkpoint section in `docs/M0.md`.

## Implementation after the plan is presented

Proceed task by task once the plan is clear. Before changing code, inspect the complete relevant call chain and establish the expected contract from source/docs/tests. Reuse existing M0 abstractions. Do not rewrite modules simply to match this prompt.

Implement only the following behaviors that are missing or incorrect:

1. **Tool contract:** Each tool has a stable identifier, description, typed input schema, permission classification, and normalized result/error contract. Use the project’s existing schema approach; do not add another schema framework without evidence it is needed.
2. **Call validation boundary:** Parse model/tool-call data strictly. Validate tool existence, required/extra fields according to the established contract, types, semantic constraints, permissions, and remaining budgets before invoking a tool. Malformed or denied requests must never execute.
3. **Bounded deterministic execution:** Enforce maximum episode steps, per-call timeout, and deterministic task reset/replay. Keep external network access and unapproved side effects disabled. Ensure exceptions are converted to typed, traceable failures without silently swallowing them.
4. **Task outcome verification:** Preserve the environment-owned success predicate as the source of truth. Do not infer task success from model claims or an LLM judge.
5. **Trace and redaction:** Preserve the existing trace schema and compatibility projections. Record the minimum fields required by `docs/M0.md` provenance contract. Apply redaction before persistence/export and test that it does not corrupt benign data or leave secrets in nested payloads.
6. **Failure behavior:** Handle unknown tools, malformed/truncated payloads, invalid arguments, permission denial, tool exception, timeout, step exhaustion, reset/replay errors, and redaction inputs explicitly. Use stable error codes/types consistent with the existing system.

Do not implement training, RL rewards, AuditKIT baseline metrics, external model downloads, deployment, or self-healing as part of this work package. If a discovered defect blocks M1.P1 but belongs to another phase, document it as a blocker and propose a separate task instead of expanding scope.
