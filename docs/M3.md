## 1. Objective

Test whether a carefully validated, environment-grounded reward can improve a reproducible SFT policy on the bounded procurement and inventory tool-use tasks. M3 covers reward specification and anti-gaming tests, a feasibility spike, and at most one bounded RL experiment with one predeclared efficiency ablation if the feasibility gate passes.

M3 does not authorize locked-test evaluation, production deployment, automatic model promotion, or unrestricted tool access. If the reward, compute, model compatibility, or matched evaluation path cannot be validated within the project schedule, record an SFT-only/no-RL decision and preserve the last valid artifact.

## 3. Scope and constraints

### In scope

- A deterministic reward implementation for the bounded tool-use environment.
- Reward-unit tests and adversarial probes for degenerate and policy-violating behavior.
- A small RL feasibility spike using the selected supported algorithm and pinned AgentTune implementation.
- One bounded RL run and one predeclared outcome-only versus outcome-plus-efficiency comparison, only if the feasibility gate passes.
- Training traces, reward component logs, checkpoints, resource measurements, validation evaluation, and a human go/revise/no-go review.

### Out of scope

- Beginning RL while M2 remains conditionally cleared or the full-scale SFT candidate/comparator is unavailable.
- Rewarding model self-reports or using an uncalibrated LLM judge as the task-success oracle.
- Locked-test access for reward design, debugging, hyperparameter selection, or checkpoint selection.
- Broad hyperparameter sweeps, multiple unplanned ablations, unbounded training, or unlogged reward changes.
- Production deployment, public release, autonomous retraining, or model promotion.

### Non-negotiable invariants

- Environment-owned deterministic outcome verification is the primary success signal.
- Tool permission, argument/schema validation, execution bounds, and terminal-state checks remain outside the learned policy and reward optimizer.
- Efficiency penalties apply only to verified successful trajectories, or use another formally bounded construction that proves a no-op cannot outscore a correct completion.
- Non-finite, missing, malformed, or unmeasured reward components fail closed; they never become a high reward.
- The held-out validation suite remains independent of reward construction. Locked-test data remains sealed.
- Evaluate baseline, SFT, and RL checkpoints under the same validated harness and report sample sizes and uncertainty. Do not claim gains from reward alone or compare different base models as a controlled experiment.

## 4. Reward design contract

Specify the reward mathematically and in code before training. A proposed decomposition may include:

| Component | Signal | Required guard |
|---|---|---|
| Format / parse | Structured output is parseable | Invalid or absent action cannot receive positive task reward. |
| Tool selection | Selected tool is permitted and task-relevant | Unknown, disallowed, or irrelevant tool is penalized; guard still blocks execution. |
| Arguments | Schema and semantic constraints pass | Invalid arguments are penalized; no invalid call reaches the tool. |
| Dependency/order | Prerequisites are respected | Score only observable, contract-defined behavior. |
| Verified outcome | Environment predicate says task completed | Primary reward signal; independent of model claim or judge. |
| Efficiency | Bounded reduction in unnecessary successful steps | Apply only to success, bounded so task success dominates efficiency. |
| Safety / policy | Violations and unsafe attempts | Enforce in trusted runtime; reward penalties are supplementary, not the safety boundary. |

For each component, document range, weight, aggregation, missing-value handling, terminal conditions, and why its scale cannot overpower verified success or safety. Avoid double-counting correlated signals. If an LLM judge is considered, calibrate it against reviewed examples and keep it secondary to deterministic verification.

### Required gaming audit

Before any optimizer run, compare the correct policy against at least these probes: empty/no-op policy, premature final answer, repeated identical calls, alternating call loop, malformed call, wrong/unauthorized tool, invalid arguments, skipped required tool, copied expected answer without executing tools, and a policy that maximizes apparent efficiency by terminating early. Tests must show that none can outrank a correct verified completion, and unsafe calls remain blocked regardless of score.

## 6. Execution protocol

1. Recheck M2 G2 status and all M3.P0 prerequisites. If any blocker remains, stop M3 training work and record the SFT-only fallback or remediation plan.
2. Audit the actual selected AgentTune release/API and algorithm support. Pin versions and cite the inspected source; do not assume CLI flags, model support, or algorithm behavior.
3. Write the reward specification and independent expected-score table for correct and adversarial policies. Define the no-op, invalid-call, and safety invariants before implementation.
4. Implement the reward as a small deterministic component over trusted structured trajectory/verifier data. Reject non-finite inputs and unknown states. Keep reward computation separate from tool authorization and evaluation metrics.
5. Run focused reward tests and the gaming audit before using a trainer. Inspect reward/outcome disagreement cases and fix or stop if proxy reward can rise while verified success falls.
6. Run a short feasibility spike with strict max steps, wall-clock/resource limits, checkpoint reload verification, periodic sample review, and explicit stop conditions.
7. Proceed to the bounded experiment only after a documented human go. Freeze configs and ablation before examining the final validation results. Do not make repeated untracked looks at validation.
8. Evaluate selected checkpoints with the same model runtime and validation contract as the matched baseline and SFT run. Do not use locked-test artifacts.
9. Review per-task traces, failure categories, safety events, reward component distributions, verified outcomes, and regressions. Human review decides whether to retain an RL candidate; training reward alone cannot select it.

### Stop conditions

Stop the run and preserve its logs/checkpoint if any of the following occurs:

- M2 entry evidence becomes invalid, provenance changes, or the model/checkpoint cannot be loaded reproducibly.
- Reward gaming probe succeeds, unsafe/disallowed tool execution occurs, or reward and verifier outcomes diverge without explanation.
- NaN/Inf reward, loss, gradients, or parameters; empty/invalid trajectory batches; uncontrolled loops; or unexpected data leakage.
- Runtime, memory, compute spend, or project schedule exceeds the approved cap.
- Validation task IDs or evaluation controls change after results are observed.

## 7. Evaluation and acceptance criteria

Compare the matching untuned base, validated SFT checkpoint, and RL checkpoint on identical validation tasks and controls. Keep locked test unavailable. Report:

- Verified task success (M1), descriptive uncertainty, exact task count, missing/failed count, and paired difference where valid.
- M2 tool selection/coverage, M3 schema/semantic validity, M4 dependency/order, M5 success-conditioned steps, M6 duplicate calls, and M7 loops/stalls, including call counts and vacuous/unmeasured denominators.
- Reward component distributions and relationship to verified outcomes, including high-reward failures and false-positive reward cases.
- Six-class failure diagnosis with representative reviewed traces, plus safety/policy violations and recovery behavior.
- Runtime, memory, token/step costs, hardware, seed, model/checkpoint/data/config/code hashes, dependency revisions, evaluator mode/version, and exact commands where actually captured.
- Limitations from small samples and repeated validation use; do not claim statistical significance without a suitable predeclared method and adequate evidence.

Gate G3 passes only if the reward gaming audit passes, the run is reproducible and within budget, no critical safety or data-integrity issue occurs, and validation shows no breach of the predeclared task-success/safety floor. Any claimed improvement must be supported by the matched evaluation, not proxy reward. If evidence is insufficient or results regress, record revise/no-go and preserve the SFT-only path.

## 8. Artifacts and provenance

Create a unique immutable run directory under `results/runs/<run_id>/` for each feasibility or RL run. Include:

- `run_manifest.json`: status, purpose, timestamps, model/revision, base and adapter identifiers, algorithm, evaluator mode, split/task IDs, seed, hardware, resource limits, and command.
- Exact training/reward/algorithm configuration, code revision, dependency lock/version report, dataset and manifest hashes.
- Versioned reward implementation reference, reward-unit-test results, gaming audit results, and expected-score matrix.
- Step-level reward components, training logs, resource profile, sampled redacted traces, checkpoint(s), and reload result.
- Validation JSON/CSV, M1–M7 report, failure breakdown, reward/outcome correlation analysis, and human review decision.

Never overwrite M2 or earlier run artifacts. Exclude credentials, restricted data, and unnecessary personal data from persisted outputs.

## 9. Risks and mitigations

| Risk | Mitigation | Trigger / response |
|---|---|---|
| M2 candidate is only a test double or cannot reload | Require full-scale compatible SFT plus matching baseline before M3 | Keep M3 blocked; complete M2 remediation or stop at SFT-only. |
| Reward optimizes a proxy | Deterministic verifier, component logs, gaming probes, trace review | High-reward failure or divergence → stop and redesign reward. |
| Efficiency term rewards premature termination | Apply only on success or prove a bounded construction | No-op outscoring success → reject reward. |
| Native AgentTune algorithm/API differs from assumptions | Inspect and pin actual implementation | Unsupported route → feasibility no-go; do not substitute silently. |
| Validation overfitting from repeated looks | Predeclare ablation/checkpoint criteria; log every evaluation | Unplanned tuning → invalidate confirmatory claim and document. |
| Compute or timeline is insufficient | Early bounded resource spike; preserve SFT-only fallback | Budget cap reached → stop RL and report. |
| Safety layer is conflated with reward penalty | Keep tool guards and verifier outside optimizer | Any unsafe call executes → halt and investigate runtime boundary. |
