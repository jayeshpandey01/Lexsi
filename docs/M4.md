## 1. Objective

Prepare a reproducible, honestly scoped SFT-only project package and determine whether any model artifact is suitable for a final release benchmark. M4 covers validation analysis, robustness and operational checks, a controlled locked-test decision, documentation/demo packaging, and the human Gate G4 review.

The full-scale SFT run `sft_aya_3b_001` is reported at 0/10 validation task success and 0/10 tool calls. It is not a passing capability candidate and must not be described as an improved or release-ready agent. The project may package its verified engineering contributions—synthetic data pipeline, collator, reward engine, safeguards, and evaluation spine—while presenting model limitations and the failed SFT outcome clearly.

M4 does not authorize RL, automatic deployment, or public publication before the applicable human and license reviews. Locked-test data remains sealed until the release benchmark gate explicitly approves one final evaluation; if no eligible candidate exists, defer the locked-test run and record why.

## 3. Scope

### In scope

- Reconcile M3 handoff evidence and update contradictory status claims.
- Run a validation-only baseline/SFT matrix where compatible model, runtime, and evaluator paths are available.
- Analyze task failures and review representative redacted traces.
- Exercise injection, malformed output, invalid tool/arguments, timeout, loop, recovery, and guard-boundary cases.
- Measure latency, throughput, memory, and cost under a declared workload where measurable.
- Decide whether a candidate qualifies for one locked-test benchmark; preserve the locked split if it does not.
- Prepare a reproducible SFT-only research package, model/data documentation, demo, and release decision.

### Out of scope

- RL, reward tuning, or more SFT/hyperparameter iterations under this milestone.
- Validation/test-driven prompt, model, reward, or checkpoint tuning.
- Treating loss reduction, syntactically valid output, or plumbing tests as task success.
- Public upload or production deployment without license, privacy, security, and human release approval.
- Locked-test access before all candidate selection, robustness work, and release controls are frozen.

## 5. M4.P1 validation protocol

Use only the validation manifest for this work package. Do not read or use the locked-test manifest contents.

1. Verify the exact base and adapter identities, immutable revisions, tokenizer/template, runtime, tool definitions, parser, verifier, decoding parameters, episode budgets, validation task IDs, and evaluator mode.
2. Run the untuned `CohereLabs/tiny-aya-global` base and `sft_aya_3b_001` candidate on identical validation tasks and controls if both paths can be loaded and executed. Do not compare the SFT candidate to Command R as a causal before/after result.
3. Persist a new immutable run per model under `results/runs/<run_id>/`, including manifests, configs, task-level results, redacted traces, metrics, failure labels, exact commands, and hashes.
4. Report M1–M7 with counts and denominators, missing/failed tasks, unmeasured values, uncertainty where meaningful, and the evaluator identity/mode. Explain vacuous metrics when no tool calls occur.
5. Classify results as exploratory if the validation set influenced selection or iteration. With only ten validation tasks, do not claim broad generalization or significance without a valid predeclared analysis.
6. Review all failures and select representative redacted traces. Do not tune based on this evaluation; any future iteration requires a separately tracked decision and new held-out evidence.

### Candidate eligibility rule

The currently reported SFT candidate has M1 = 0/10 and M2 = 0/10. Unless new valid evidence supersedes that report, it is not eligible for promotion or locked-test evaluation. M4 may still complete validation diagnosis and package the training/evaluation infrastructure as research artifacts.

## 6. Locked-test and release controls

Locked-test evaluation is a single final benchmark action, not a debugging or selection loop. Before access, reviewers must verify:

- validation matrix and robustness review are complete;
- the exact candidate, model revision, adapter, prompt, decoding settings, tools, parser, verifier, and metrics are frozen;
- candidate eligibility and success/safety thresholds were set without locked-test data;
- no prompt, reward, checkpoint, or hyperparameter changes will follow the result;
- an authorized evaluation owner, immutable run location, redaction plan, and analysis procedure are recorded.

If the candidate fails eligibility, there is no locked-test run in M4. Record the deferral and retain the split for a future approved candidate. G4 can conclude no-go without test access.

## 7. Packaging requirements

The package must distinguish **verified engineering artifacts** from **model capability evidence**. Include, as applicable:

- Setup and reproduction instructions with pinned versions and exact commands.
- Dataset card, provenance/license status, split policy, hashes, and train-only restrictions.
- Model card identifying the base revision, adapter, training method/data, quantization, evaluation, intended use, and limitations.
- Validation metrics with sample size and failure analysis; clearly state 0/10 success if unchanged.
- Reward specification and anti-gaming tests, labeled as reward verification rather than proof of model capability.
- Safety boundaries, known failures, demo script, and reproducibility checklist.
- Only redacted and license-cleared artifacts; no credentials, private inputs, or prohibited dataset material.

Do not publish the adapter or dataset until the base-model and dataset licenses, attribution requirements, access terms, and project release rules are reviewed. If public release is not cleared, provide a local reproducibility package and document the restriction.

## 8. Gate G4 acceptance criteria

Gate G4 requires a human-reviewed decision based on:

- accurate M3 handoff and provenance;
- validation evidence and limitations reported without overclaiming;
- robustness/security findings with no unresolved critical guard bypass;
- operational profile and documented constraints;
- locked-test use either completed once under the approved protocol or explicitly deferred because no eligible candidate exists;
- reproducible, license-reviewed, redacted package;
- rollback, owner, and release scope appropriate to evidence.

Possible outcomes are **GO**, **LIMITED PILOT**, or **NO-GO**. A GO or limited pilot is not justified by a passing unit test suite, falling training loss, or test-double smoke run alone. Production readiness requires separate evidence and approval.

## 9. Risks and responses

| Risk | Response | Trigger / action |
|---|---|---|
| M3 report has contradictory historical claims | Reconcile against run artifacts and preserve history | Do not make final claims until corrected with an audit trail. |
| No matched Tiny Aya base evaluation | Run matched validation only if executable | Do not claim comparative SFT gains; document missing comparator. |
| SFT candidate has 0/10 success | Treat as failed capability candidate | Do not select it for locked test or promotion without new valid evidence. |
| Small validation sample is overfit or noisy | Label exploratory; state N and uncertainty | Avoid generalization/significance claims. |
| Locked test is used to tune or debug | Single-use gate, access record, frozen protocol | Any tuning after exposure invalidates confirmatory use. |
| License/privacy or artifact provenance is unclear | Review before publishing | Hold external release; keep local package if permitted. |
| Safety regression or guard bypass | Stop release path and investigate | Gate G4 no-go until remediated and re-reviewed. |
