# M5 — Capability Remediation Research and Candidate Re-evaluation

> **Milestone:** M5<br>
> **Project:** Reliable and Efficient Tool-Using Agent<br>
> **Status:** In Progress (P0–P4 Complete; P5 In Progress; P6 Gated) — Remediation research cycle executed; candidate evaluation complete; capability floors unmet (M1=0.0%); NO-GO recommended; not a completed milestone.<br>
> **Schedule:** Active 30-day research cycle, D31–D60; dates are relative to M5 kickoff. The separate hackathon submission deadline currently listed by the official site is November 14, 2026 (end of day AoE); it must not be confused with this research-cycle schedule.<br>
> **Predecessor:** M4 Gate G4 review prepared; recommended NO-GO for model promotion; reviewer signatures pending. See [`M4_P6_gate_review.md`](M4_P6_gate_review.md).<br>
> **Scope boundary:** Research and candidate development only. No production deployment, external publication, or locked-test access is authorized by this plan.

## 1. Objective

M5 addresses the capability failure observed in M4 by investigating why the current SFT candidate does not invoke tools, then—only after human approval—designing and evaluating a separately versioned candidate on permitted training and validation data. M5 is successful if it produces a reproducible, evidence-based candidate decision, including a documented no-go if capability or safety requirements remain unmet. Improvement is not assumed.

M4 established that `sft_aya_3b_001` achieved M1=0/10 and M2=0/10 on ten validation tasks, with 10/10 `EarlyTerminationFailure`. The matched untuned base-model validation comparator was blocked. The existing Command R `baseline_run_001` is exploratory and incommensurable. M5 must not claim causal improvement from those comparisons.

The hackathon submission is a separate, time-bound deliverable. The current official event page lists a November 14, 2026 submission deadline and requires a public project/demo, multiple before/after metrics, a methodology write-up, and public Hugging Face collections for created artifacts. These requirements may conflict with this project's current model/data distribution restrictions and missing matched comparison. M5 must report those conflicts plainly; it must not weaken evaluation, licensing, privacy, or human-approval controls to meet the event date. See the current [official hackathon page](https://hackathon.lexsi.ai/) and the requirement audit produced under M5.P2.

## 2. Entry conditions and constraints

M5 work starts with documentary and diagnostic work only. Before any new data generation, training, or validation run, project leadership must approve the cycle, assign accountable named owners, confirm compute and budget, and approve a preregistered protocol and data-use plan.

1. Preserve M4's records and the current adapter as immutable historical evidence.
2. Do not read, inspect, score, hash, or use the locked-test manifest or its contents. The M4 `DEFER_LOCKED_TEST` decision remains in force.
3. Do not use validation results to tune repeatedly. Define candidate, controls, thresholds, run budget, and analysis before the next validation evaluation.
4. Keep the base comparator requirement explicit. If an identical-protocol base rollout cannot be run, report the limitation and make no causal SFT-improvement claim.
5. Do not assume that additional synthetic examples, instruction data, or more optimization steps will improve task success. Document provenance, deduplication, leakage controls, and evaluation rationale.
6. Training, model access, data redistribution, and artifact publication remain subject to license, privacy, compute, and human review.
7. No external distribution or production release is authorized by M5. Gate G4 must be formally revisited by authorized reviewers before any separate release decision.

## 3. Scope

### In scope

- Audit the existing training examples, serialization/chat template, tokenizer, target masking, rollout parser, and termination behavior to identify testable hypotheses for early termination.
- Review relevant literature and primary implementation documentation when proposing changes to training format, data composition, or evaluation protocol; record sources and applicability.
- Produce a preregistered remediation proposal with bounded alternatives, controls, measurable outcomes, resource estimates, and stop criteria.
- If separately approved, build a versioned training-only dataset and run bounded training experiments under immutable run IDs.
- Evaluate a frozen candidate on validation data using the existing evaluator, reporting M1–M7, counts, denominators, failures, uncertainty, and matched-comparator status.
- Review safety, reproducibility, model/data provenance, and operational constraints before making a candidate recommendation.

### Out of scope

- Any access to or use of locked-test content without a new explicit, signed release protocol after all eligibility criteria pass.
- RL, reward redesign, broad hyperparameter search, or unbounded data/training expansion.
- Treating lower loss, correct formatting alone, plumbing tests, or harness demonstrations as task success.
- Public release, adapter upload, production deployment, or pilot operation.
- Rewriting M4's historical results to imply they were successful or matched.

## 5. M5.P1 protocol: failure diagnosis and preregistration

M5.P1 is analysis and planning only. It must not launch training, tune a model, rerun validation, or inspect the locked test.

1. Read the controlling M4 candidate evaluation, M3 handoff, M2 training/data documentation, model and data cards, relevant source code, and training run artifacts. Preserve existing working-tree changes.
2. Trace the data path end to end: source example → serialized conversation → tokenizer/chat template → labels and loss mask → checkpoint → generation configuration → parser/orchestrator action recognition. Record the exact files and evidence supporting each observation.
3. Distinguish observed facts from hypotheses. The observed failure is early termination with zero tool calls on the M4 validation run; root-cause explanations must be tested, not asserted from symptoms alone.
4. Review primary research and official implementation documentation for any proposed change. Record stable citations, the claim each source supports, and limitations for this project.
5. Propose a small, bounded experiment matrix with a control and one interpretable change per condition. Define data provenance, training budget, seeds, immutable run naming, validation exposure rules, capability floors, safety criteria, and stop criteria in advance.
6. Assess whether and how an identical-protocol untuned base rollout can be obtained. If infeasible, state that causal comparison will remain unavailable.
7. Identify required human decisions: authorization to create/expand data, gated model access, compute budget, license review, named owners, and permission to execute bounded training/evaluation.
8. Create `docs/M5_P1_failure_diagnosis.md` containing the evidence map, data-flow trace, observed failure, competing hypotheses, research notes, proposed preregistration, resource estimate, risks, and explicit approval gates.
9. Update the M5.P1 tracker status only to the level supported by completed evidence. Do not mark implementation, training, or evaluation complete.

### M5.P2–P6 execution controls

1. **P2 is a gate, not an automatic launch.** It must determine whether data use, new training, matched-base evaluation, and public submission are each authorized and feasible. Record the hackathon deadline independently from the 30-day M5 schedule.
2. **P3 requires written approval.** Do not generate/expand training data, access gated models, train, evaluate, upload artifacts, or submit to the event based only on this plan. Approval must identify scope, owners, resources, and permitted artifact destinations.
3. **P4 uses a frozen candidate and protocol.** Any validation run after candidate selection is reported with its exposure/history and cannot be called confirmatory if it informed further tuning.
4. **P5 checks submission readiness, not just document presence.** Verify public links only after authorized publication; verify clean-clone reproduction only by actually performing it; verify hashes and licensing against source records. Otherwise mark the item BLOCKED or NOT VERIFIED.
5. **P6 separates submission compliance from model release readiness.** A submission may not be called fully compliant if required public artifacts or demonstrated before/after improvement are missing. A human must decide whether to submit a transparently limited project or not submit; no agent may represent missing evidence as satisfied.
6. The hackathon submission deadline does not waive the locked-test deferral, M4 Gate G4 signature requirement, model/data license review, or the prohibition on unsupported claims.

## 6. Candidate evaluation and progression gates

Any future candidate must use a frozen protocol and meet at least the existing predeclared validation floors before a locked-test request is considered:

- M1 verified task success ≥ 40%.
- M2 tool selection accuracy ≥ 50%.
- M3 argument schema validity = 100%.
- M7 loop/stall or critical policy violation rate = 0% under the declared evaluator.
- Matched base comparator completed under identical conditions for causal improvement claims.
- Robustness, license, provenance, redaction, and human review requirements satisfied.

Passing these floors does not itself open the locked test. A separate authorized release protocol must freeze the candidate and evaluation plan, name the evaluation and safety owners, document single-use controls, and receive explicit written approval. If any floor is missed, retain the locked split sealed and record a no-go for that candidate.

## 7. Evidence and reporting requirements

Every executed experiment must be stored immutably under `results/runs/<run_id>/` with, as applicable:

- Run manifest, owner, timestamp, purpose, status, exact command, environment, and source revision.
- Model and adapter identity/checksum, tokenizer/template, decoding settings, and tool/parser/verifier versions.
- Dataset identity, split, provenance/license, hashes, task counts, and leakage audit.
- Training configuration, seed, compute/runtime, logs, checkpoints, and selection rationale.
- Task-level outcomes, redacted traces, M1–M7, denominators, uncertainty, failure labels, and evaluator mode.
- Deviations from preregistration and their impact on confirmatory claims.

Report unavailable metrics as unavailable. Do not infer model-serving performance from deterministic harness benchmarks. Separate component/safety evidence from autonomous task capability.

## 8. Risks and responses

| Risk | Response | Trigger / action |
|---|---|---|
| Root cause inferred from a single symptom | Keep multiple falsifiable hypotheses and inspect the complete data/generation path | Evidence does not discriminate → do not train; refine diagnosis |
| Expanded data duplicates existing patterns or leaks validation | Train-only generation, provenance, deduplication, split audit | Any overlap or unclear provenance → block dataset/run |
| Repeated validation tuning inflates results | Freeze protocol and run budget before evaluation | Any post-result tuning → mark exploratory and require new held-out evidence |
| No matched base model available | Budget and test base rollout feasibility before candidate comparison | Comparator blocked → prohibit causal improvement claims |
| Candidate remains incapable despite lower loss | Use verified task success floors as the primary gate | Floor missed → stop candidate promotion path |
| License/access constraints prevent training or sharing | Review terms before access, data use, or distribution | Unclear terms → hold affected activity/artifacts |
| Timeline or compute is insufficient | Bound experiment count and compute before cycle approval | Budget exceeded → stop and report, do not silently extend |
| Locked-test contamination | Keep test manifest sealed and access-controlled | Accidental exposure → stop, record incident, invalidate confirmatory use |
